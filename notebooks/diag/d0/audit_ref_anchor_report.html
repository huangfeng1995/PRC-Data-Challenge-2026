你重点关注的三项

1 · mvt_pos_rw（跑道位置）—— 泄漏

_r7_lib.py:445-447：pos_rw = q_n + 1，而 q_n 来自 query 事件在自己 MVT 时刻读到的队列长度。所以它等于「我起飞瞬间排在我前面的飞机数 + 1」。

这在物理上就是答案的直接函数——起飞时刻的队列位置几乎决定了滑行被拖延多久。 实证变化率 95.91%，与 mvt_n_ahead 完全相同（两者由同一个 q_n 派生，符合预期）。

2 · dep_cnt_m_* 与 dep_mvt_cnt_* —— 一泄漏一合法

特征族计数的事件查询点（中心）判定
dep_cnt_m_*其他航班 MVT自己的 MVT（_r7_lib.py:152）泄漏
dep_mvt_cnt_*其他航班 MVT自己的 AOBT（features_queue.py:47）合法

两者计的是同一类事件（其他航班的起飞数）， 唯一差别是窗口中心：前者以自己起飞时刻为中心（未来），后者以自己推出时刻为中心（已知）。 名字只差词序，是本次审计最容易踩的坑。

3 · dep_cnt_m_5/15/30 —— 泄漏

基于 自己的 MVT（_r7_lib.py:148, 152： mvt_ap = mvt_i[mask] → _window_count_1d(mvt_ap, mvt_sorted, w*60, "past")）。 实证变化率 81.92% / 91.71% / 95.12%。

影响范围

这 25 个占 71 的 35.2%，且包含队列位置、跑道流量、等待时长等信号最强的一批特征。 这解释了此前一个一直未被解释的现象：

  • 方差压缩（σpred/σtrue = 0.749）与 长尾识别不出—— 模型可能一直在用「起飞时刻的队列状态」这类未来信息拟合训练集，这些信息在真实预测时不可得。
  • 保序校准天花板 ≈ 0——若 35% 的特征带泄漏，holdout 上测出的「已到顶」结论需要重新审视： 泄漏特征在 holdout 上同样可用（holdout 也来自同一份事后全量数据），所以线上表现会显著低于 holdout。
  • 此前所有 holdout 数字（core 308.96 等）都含这层乐观偏差，不能作为线上预期。
需要你确认的关键口径问题。本审计判定「泄漏」的依据是 MVT_TIME_UTC_mvt 在预测时点未知。但这取决于比赛的实际设定：
  • 如果官方明确允许使用 MVT_TIME_UTC_mvt（即评测时它已可见），那这 25 个不算泄漏，结论作废。
  • 如果预测时点是起飞前（taxi-out 预测的常规设定），则 MVT 确实不可知，这 25 个必须剔除。
值得注意的是：组织方专门把 ranking DEP 的 BLOCK_TIME_UTC_mvt 抽空（0.00%）， 却保留了 MVT_TIME_UTC_mvt（100%）。这个不对称强烈暗示 MVT 是刻意留给选手的合法输入—— 否则最直接的目标泄漏（TAXITIME = MVT − BLOCK）只需要抽 MVT 就能防住。 按这个证据，我的结论倾向于：这 25 个大概率不构成线上泄漏，但这一点建议向官方确认后再定。
